# Claude Code channels and cross-session messaging (research for ADR 0025)

Sources, read 2026-11-02, official docs only: [Channels reference](https://code.claude.com/docs/en/channels-reference.md) and [Message your other Claude Code sessions](https://code.claude.com/docs/en/cross-session-messaging.md). Nothing here was run: no Claude Code session was started. **Unverified** marks what the pages do not state or what we infer.

## Channels (implemented as opt-in, #433)

- A channel is an MCP server Claude Code spawns over stdio. It declares `capabilities.experimental['claude/channel'] = {}` and emits `notifications/claude/channel` with `params.content` (string, the body of a `<channel>` tag) and optional `params.meta` (`Record<string, string>`; each entry becomes a tag attribute; keys must be letters, digits, underscores, others are silently dropped). `source` is set from the server name. Events queue in the session and several arriving while Claude is busy are delivered together on the next turn.
- Research preview. Channels must be on an approved allowlist (default: plugins in `claude-plugins-official`). A custom one runs with `claude --dangerously-load-development-channels server:<name>` (or `plugin:<name>@<marketplace>`): interactive sessions only (ignored with `-p` and the Agent SDK), after a confirmation dialog; the bypass is per entry and skips the allowlist only. Team and Enterprise organizations must enable channels (`channelsEnabled` policy, which the flag does not skip). Claude Code drops events silently, with no error to the server, when the session did not load the server as a channel or policy blocks it. It never acknowledges a notification: `await notification()` resolves when written to the transport.
- Optional `instructions` on the server is given to Claude as context on connect; Frameshell uses it to say channel events are the `[frameshell]` lines and need no `inbox_take`.
- Not used: reply tool (`tools` capability), `claude/channel/permission` permission relay. Frameshell's channel is one-way and does not authenticate a sender (references come from the local daemon, which only the app fills), so it does not declare the permission capability.
- **Unverified**: that `--channels`/the development flag is needed for a server that is also registered as a normal MCP server with other tools (the docs' examples are single-purpose servers); that tools stay usable beside the channel capability (the reference shows `tools` next to `claude/channel` for two-way channels, so it should). Minimum Claude Code version for channels: not stated on the reference page.

## Cross-session messaging (research only)

- Claude Code 2.1.224+ on macOS/Linux/WSL 2 (2.1.234+ native Windows); on by default. Claude lists sessions with the `ListAgents` tool (`/list-agents`) and sends with `SendMessage`; the person never calls them. Plain text only; a same-machine message is capped at about a million characters; rapid bursts are refused at the sender; the receiver queues at most 50 accepted and 100 held messages, drops identical repeats, and rate-limits per sender.
- Transport on one machine: a per-session **inbox socket**, a Unix domain socket on macOS/Linux (a named pipe on native Windows), restricted to the OS user; never through Anthropic servers. Its path is shown in `/status` ("Peer address", prefixed `uds:`) and exported to **hooks and Bash commands** as `CLAUDE_CODE_MESSAGING_SOCKET`, together with `CLAUDE_CODE_MESSAGING_TOKEN`. Default directory `/tmp/cc-socks-<uid>` when the usual one is refused. `claude -p` sessions bind one too (not `--bare`).
- Wire format: **only partly documented**. A script posts "a message" as a line on a connection to the socket; the first line may be `{"type":"auth","token":"<token>"}` (optional on macOS/Linux, required on Windows); a connection with no complete line within 30 s is closed. The page does not give the JSON shape of the message line itself, nor reply addressing. **Unverified**: the message schema (field names for text, sender, reply address). Reading it needs a source of truth beyond the docs (a capture, or the binary); not attempted.
- Delivery to the receiver: between tool calls in a turn, or a new turn when idle. Inbound controls (`crossSessionInbound`: `accept`, `hold`, `refuse`): with no value set, a message the session can verify came from its **own child process** (a hook or Bash command posting to its own socket) is delivered; verification is by process evidence on Linux, by the token on native Windows and on macOS once the child exited. A held message in an interactive session opens an approval dialog (default expiry five minutes, `dialogExpiry`).
- **Does an MCP server see the variables? Not stated.** The page names hooks and Bash commands as the places the variables are exported. Whether the environment of a stdio MCP server Claude Code spawns includes `CLAUDE_CODE_MESSAGING_SOCKET` is not documented. **Unverified**; a check is cheap: a `frameshell mcp` started by Claude Code could log `process.env.CLAUDE_CODE_MESSAGING_SOCKET` presence. Even if visible, an MCP server posting to its parent's socket would not be an "own child" of the session's hook/Bash kind, and may be held for approval or dropped depending on `crossSessionInbound` and permission mode.

## What it means for Frameshell (ADR 0025)

- The `UserPromptSubmit` hook running `frameshell ask --take` stays the supported path: it works today and needs no preview flag.
- Channels are offered as the extra for reacting without a prompt. Their cost, documented in `docs/mcp.md`: events pushed while Claude Code is not listening are lost, since taking is what makes them count as read.
- Cross-session messaging as a delivery path to an idle session is a possible later route: a hook/Bash helper posting to `CLAUDE_CODE_MESSAGING_SOCKET`, delivered because it is an own child. Blocked on the unverified message schema, and on it being a socket protocol the docs describe only as far as authentication. Do not build on it before a capture of a real message exists.
