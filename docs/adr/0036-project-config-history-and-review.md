# Project config changes in history and review mode: one config journal of keyed operations

#496 (follow-up of #469 / PR #495, owner decision 14 on #469; epic #451) asks that changes of project config (`formats` of `frameshell.json` today, `style.json` with `style set` next, #468 S3) behave like timeline changes: listed by `history`, undone by `revert` and `tx abort`, and held by review mode. The owner chose option A on 2026-11-11, with every recommendation of the draft (the eight points below, from the ticket's decision comment). Slice 1 implements the journal, history and revert for formats; slice 2 holds config changes in review-mode proposals and journals `file.write` of `frameshell.json` formats.

## Context

- `FormatService` (`packages/core/src/formats.ts`) journaled each format edit in `.frameshell/history/project.config.jsonl` as `{ id, op, args, author, at, before, after, undo }`: the whole list before and after and the call that undoes it, with no transaction and no hash chain.
- Stopgaps of ADR 0027 decision 11: `revert` of a format change's op id was refused (InvalidOperation, reason `format change`) naming its `undo` call, and while review mode is on `format.add`/`format.remove` from anyone but `ui` are refused with ProposalState `forbidden`.
- Timeline history (SPEC §6.2) is one journal per timeline with a `timeline.patch` inverse and a hash chain of the timeline; `planRevert` (`history/revert.ts`) is pure over `TimelinePatch` with entity keys `group:`, `track:`, `clip:`, `marker:`, `order`. `TransactionTracker` records `{ root, timeline }` per open transaction for `tx abort`.
- Review mode (ADR 0019) holds timeline parts and new timeline files only. `file.write` validates `frameshell.json` and `style.json` but neither journals them nor routes them through review.
- Nothing in the app shows a format or style visually yet (no preview format switcher, ADR 0027 slice 2), so a config change has no visual After.

## Decision

1. **Journal.** Project-config changes stay in their own journal, `.frameshell/history/project.config.jsonl`, separate from the timeline journals. Entries gain `doc`, `patch: [{ key, before, after }]`, `tx`, `txLabel`, `hashBefore`/`hash` of the document section and `proposal`.
2. **Keyed operations, not snapshots.** Keys `format:<id>` (entry plus list position; the primary format is never a key) and `style:<dotted leaf path>`. A pure `planConfigRevert` mirrors `planRevert`: a later foreign op on the same key conflicts, a hash gap means an edit outside the journal.
3. **One transaction = one proposal.** A proposal gains a `config` part next to `parts` and `files`. A transaction mixing clip ops and a format or style change is one proposal, accepted or rejected whole. Rebase replays when the person's config changes since base touch none of the proposal's keys; otherwise stale with those keys as `conflicts`.
4. **Before/After.** A text list in the proposal bar ("+ 9x16 (1080x1920)", "colors.accent A → B"), plus `view: proposal` on `format.list`, `style.show` and `frame --format`. The visual After arrives with the format switcher and style consumers.
5. **`file.write` of `frameshell.json`/`style.json`.** Diffed into keyed config ops, journaled and routed through review (as ADR 0019 §9 does for timelines): `formats` of `frameshell.json` since slice 2, `style.json` since slice 4.
6. **Style key granularity.** Leaf paths; string arrays (`notes`, `rules`, `banned`) are one key each.
7. **History panel.** Config transactions show in every timeline's History, with a config mark, because a format change affects every timeline's export.
8. **Old journal lines** are not migrated on disk: they are read as patches of `format:<id>` keys, each its own transaction.

`style set` (#468 S3, ADR 0028 decision 6) is built on this journal only (`ConfigJournal`); brand capture (#467) reuses it.

## Considered options

- **B. Whole-document snapshots in proposals and journal.** Rejected: any change by the person to the same file makes an agent's proposal stale (the rule ADR 0019 rejected for timelines), and revert of an older change becomes impossible after any later change to the file.
- **C. Config operations in the timeline journal** (main timeline or a pseudo-timeline). Rejected: timeline entries carry a timeline hash chain and a `timeline.patch` inverse config cannot fill, and every timeline consumer would have to skip config entries.
- **D. Replay the stored undo calls.** Rejected: each config service would carry its own conflict and rebase rules, and a replay on a changed base can succeed with another effect than proposed.

## Consequences

- **Code (slice 1):** `packages/core/src/config/`: `patch.ts` (keyed diff and apply, `ConfigRules`), `project-doc.ts` (the `project` document: `formatState`, `FORMAT_RULES`), `revert.ts` (`planConfigRevert`), `journal.ts` (`CONFIG_JOURNAL`, `readConfigJournal` with the legacy reader, `ConfigJournal`: one queue per project, `commit`, `planRevert`). `FormatService` writes only through the journal (since slice 2 via `TimelineService.changeConfig`); the hash is `contentHash` of the keyed state (`history/hash.ts`, shared with `timelineHash`).
- **Format keys:** the value of `format:<id>` is `{ id, width, height, index }`. A format that only moved because another was added or removed before it did not change (`FORMAT_RULES.same` compares id and size), so adding `9x16` never conflicts with the person adding `1x1`. Writing a key inserts the format at its `index` (clamped) and renumbers, so reverting a removal puts it back where it was.
- **Legacy lines** (`before`/`after` lists, no `patch`): read as a diff of their lists with transaction id `tx_<hex of the op id>`, hashes computed from the lists.
- **History:** `history` merges config operations into a timeline's listing by time, grouped under their transaction, each with `doc: "project"`, its keys as `touched`, and `revisionBefore` = `revision` = the timeline's revision at the time. `since` finds transactions in either journal. `history.diff` of a config-only target returns no clips.
- **Revert:** `revert <tx|op>` undoes config operations of the target, and its operations on the named timeline when that journal holds some, in one standalone transaction. Config is planned first (conflicts and hash gaps refuse before anything is written), then the timeline is reverted, then config is written. A config-only revert returns the config `revert` as `operation` with an empty `timeline.patch` inverse and an unchanged `revision`; the result's `config` lists the config `revert` operations. A target that also changed other timelines is reverted one timeline per call: the first call reverts its config too, later calls skip config while that `revert` stands (`configReverted`), and a timeline the target never changed is HistoryNotFound naming the timelines it did (`data.timelines`), also from `history.diff`. A config write can still throw after the timeline was reverted (the file fails validation); planning first makes that unlikely, and the timeline then stays reverted.
- **Transactions:** `TransactionTracker.touched` holds `{ root, timeline }` or `{ root, doc }` (persisted open transactions of an older daemon still parse). `tx abort` plans config reverts before the timelines and writes them after, all or nothing; its result gains `config`. A config root whose change failed journaled nothing, so it is neither undone nor refused in review mode.
- **Stopgap of slice 1, removed in slice 2:** while review mode was on, `format.add`, `format.remove`, `revert` of a target holding config, and `tx abort` of a transaction that changed config were refused for anyone but `ui` with ProposalState `forbidden`.
- **Wire** (`PROTOCOL_VERSION` 89): `format.add`/`format.remove` results gain `tx`; `history` operations gain `doc`; `revert` and `tx.abort` results gain `config`; `revert` no longer throws reason `format change`. New protocol schemas `ConfigJournalEntrySchema`, `ConfigOperationSchema`.
- **App:** History rows of a transaction that changed config carry a `project` mark; `format.add`/`format.remove` have verbs; the list reloads after a revert from the panel, since a config-only revert keeps the timeline revision. It does not yet reload when someone else changes only config.
- **Not migrated:** old journal lines stay as written.
- **Code (slice 2):** `TimelineService.changeConfig` is the one way config changes are made (a `ConfigChanger`, `config/journal.ts`): for `ui`, or with review mode off, it journals and writes; otherwise `#route` gives the transaction's proposal and the change is made on its version of the document. `FormatService` computes each change on the state it gets (file or proposal), so the same rules check both. A proposal file gains `config: [{ doc, base, ops }]` (`ops`: id, op, args, keyed `patch` from the proposal's version before to after, `undo`, time); the shadow is rebuilt from `base` on load. `#syncConfig` rebases like `#sync`: the person's keys since `base` that the proposal also touches make it stale with those keys as `conflicts`, else its `after` values replay on the file's state, then `ConfigDocument.check` (a format named like a new primary) can still make it stale. Accept and reject hold `ConfigJournal.serial` around the timelines' locks; accept syncs every part first, then journals the config operations under their proposed ids, author, transaction and `proposal`, before the timeline operations. A proposal's undo (`revert` by an agent, `tx abort` of what reached the file before review mode) is proposed the same way: `revertAll` takes the planned config reverts and routes them per project like timeline reverts.
- **Rebase position:** a replayed format keeps the `index` it was proposed at, so the person's added format can end up after it (FORMAT_RULES inserts by index, as a revert does).
- **`file.write` of `frameshell.json` (decision 5, slice 5 brought forward for `formats`):** the registry hands a validated write to the daemon (`ProjectRegistryOptions.writeConfig`). A write whose keyed formats state differs is a `file.write` config operation (`args.path`), journaled before the file is written as given; in review mode for a non-`ui` writer the formats change waits in the proposal while the other keys are written at once with the current formats (`writeConfigKeepingFormats`; refused as InvalidProjectFile when they no longer fit the new `resolution`). A write that changes nothing in formats journals nothing. `style.json` writes go the same way since slice 4 (`ProjectRegistryOptions.writeStyle`; the review-mode refusal `guardWrite` is gone). Hand edits of both files are journaled by the watcher since slice 5.
- **Code (slice 4, with ADR 0028 slice 2):** the `style` document (`packages/core/src/style/doc.ts`): keys `style:<path>` for each path of `STYLE_PATHS` plus `style:from`, `PLAIN_RULES`; values null or absent in the file have no key, and an empty state is no file. It writes only the changed keys into the file on disk. `StyleService` (`style/service.ts`) makes `style.set` and `style.apply` through `TimelineService.changeConfig` in the caller's transaction, checking the new state against `StyleFileSchema` before anything is journaled. A `style.json` `file.write` that changes a value is a `file.write` config operation written as given (at once) or held whole (review mode); one that changes no value, or replaces an invalid file, is written at once and journals nothing. `style.show` takes `view`. `revert` touches the documents its target changed (was always `project`). `ConfigDocSchema` gains `style`; `PROTOCOL_VERSION` 98.
- **Wire (slice 2):** `format.add`/`format.remove` results gain `proposal`; `format.list` takes `view` and returns `view`/`proposal`; `proposal.status`/`status` proposals and `proposal.changed` gain `config` (keys with file and proposal values); `proposal.diff` gains `config`; `proposal.accept` gains `config` (journaled config operations); decisions gain optional `config` (docs), and decided config proposals show in every timeline's `history`. Protocol schemas `ProposalConfigChangeSchema` and `ConfigDocSchema` live in `protocol/src/config.ts`.
- **App (slice 2):** the proposal bar lists the formats a proposal adds, removes or resizes (`Formats: + 9x16 (1080x1920)`, en + es); the History list reads again when a proposal opens or closes, so an accepted config-only proposal shows.
- **Code (slice 5, hand edits):** `config/direct-edits.ts`. `ConfigWatcher` watches `frameshell.json` and `style.json` at the project root (and reports each document once when the watch is live, so a file that does not exist yet has a first sight). `DirectConfigEdits.reconcile` runs in the config journal's turn: it reads the document's keyed state and compares it with the document's head snapshot, `.frameshell/history/project.config.<doc>.head.json` (`{ hash, state }`, written by `ConfigJournal.commit` after every journaled change and at a first sight). Equal hash: the daemon's own write or a change in keys no document covers, nothing to do. Different, with a head that is the journal's last (or no journal yet): `TimelineService.directConfigEdit` makes it a `file.edit` operation (`args.path`) of author `file` in a transaction labelled `Edit <file>`. With review mode off it is journaled with the file left as the person wrote it. In review mode it waits in a ready proposal of author `file` and the document goes back to the head's state (`ConfigJournal.write`; the other keys of the file stay as written); accepting journals it and writes the document, rejecting leaves the file as it was put back. When another proposal is open the edit is not taken in, like a `timeline.patch` direct edit: the document goes back and the edited file is kept as `.frameshell/rejected/<time>-<file>` (not listed by `status`, which lists timeline rejections only). A file that does not validate, or no head (a first sight, or a head behind the journal after a crash or an older daemon), journals nothing: that edit stays a hash gap `revert` refuses to cross. An edit made while no daemon ran is caught up at the next open from the head. Deleting `style.json` is an edit that clears every value.
- **`view: proposal` on `frame --format` and `review --format`:** the daemon reads the `project` document through `viewConfig` and hands the proposal's format list to `ExportService.frame`/`resolvedSubtitles` (`LoadedTimeline.formats`) and to `review`'s request, so a format only an open proposal adds can be captured and laid out; without it `FormatNotFound` names the file's formats. `cover` is primary-only and unchanged. No wire change.
- **App (slice 5):** the proposal bar lists the style values a proposal sets, changes or clears (`Style: colors.accent #1A1A1A → #FF5A00`, `none` for no value; en + es), and History titles a `file.edit` operation Direct edit.
- **Still uncovered:** other `frameshell.json` keys (plugins, export, transcription), `people.json`, `director.json`, compositions and assets, until they register as config documents.

## Implementation plan (each slice ships and is tested alone)

1. Config journal + revert for formats: keyed patch, journal with legacy reader, pure revert with conflict and hash-gap checks; `FormatService` through it in the caller's transaction; `history`, `revert <tx|op>`, `tx abort`; wire bump; CLI `history` rows; History panel mark. (This slice.)
2. Review mode for formats: proposal `config` part, routing of `format.add`/`remove`, `revert` and `tx abort`, rebase/stale by keys then document check, accept/reject writing journal + `frameshell.json`; `view` on `format.list`; `proposal.diff`/`proposal.changed` carry config; the review-mode refusal goes; skill note; plus the proposal bar text list (en + es), History reload on proposal open/close, and `file.write` of `frameshell.json` formats (slice 5 for `formats`). (Done.) `view` on `frame --format`: slice 5.
3. App: e2e of an agent's format proposal accepted and reverted from History (done, with a hand edit held and accepted: `e2e/config-proposal.spec.ts`); live History reload when someone else changes only config outside a proposal (left: the list reads again when a proposal opens or closes or after a revert from the panel, not after a hand edit applied at once).
4. `style set` (#468 S3) on the same journal: `style` document (leaf keys, `StyleFileSchema`), `style.set`, CLI, MCP, skill; `view` on `style.show`; `style.apply` and `file.write` of `style.json` through it. (Done.) Style lines in the app's proposal bar: slice 5.
5. Direct edits: on-disk edits of `frameshell.json` `formats` and of `style.json` (the watcher), diffed into keyed config ops, journaled and routed through review. `file.write` of `frameshell.json` formats is done in slice 2, of `style.json` in slice 4, the watcher in slice 5. (Done.)
