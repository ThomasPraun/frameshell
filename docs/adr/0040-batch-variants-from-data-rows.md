# Batch variants: a template timeline patched in memory per data row

#477 (epic #451) asks for `frameshell batch`: one edit, many variants (sizes, languages, product rows), each row setting clip props or swapping assets, every row rendered, and a manifest that lets a failed row be re-run alone. The owner decided option A on 2026-11-11, with every recommendation of the proposed decision accepted (the ten points below). **All slices are built: slot defaults, the review column, per-row voiceover placement and CSV rows, and slice 6 (below), which removes the limits that were left: a changed row re-renders without `force`, a slot naming an undeclared prop fails, and `batch.cancel` stops a running batch. Parallel rows stay out: a flag if real batches show idle cores.**

## Context (verified)

- `ExportService.render` read the timeline file by id, compiled and checked every format with stand-in clip renders and bakes, then queued one `render` job per format. `#resolved` already took an in-memory timeline (`frame` uses it for review-mode proposals).
- The clip render cache key covers type, source, `props`, `elements`, inputs, fps and size, so a row with other props is a new cache entry without a key change, and equal rows share one render. `ClipRenderer.ensure` takes any timeline object.
- Props are an untyped record checked by the adapter's Standard Schema (`clip.set`, `clipTypeInfo`). Typed template props are ADR 0033 slice 2 (#466), not landed.
- No engine operation swaps a media clip's `asset`; only `clip.add` takes one.
- Review mode (ADR 0019) and the journals cover timeline and config files only. Writing one timeline file per variant would bring the watcher, background clip renders, journal entries and one proposal per row.
- The general job queue runs two jobs at once, FIFO, and dedupes a queued or running job of the same kind, project, asset and output. `gc` keeps clip renders while a render or clip job of the project runs.

## Decision

1. **Template = a timeline** of the project (`template`, default `main`). A single generated clip is a one-clip timeline; there is no clip-only mode.
2. **Slots live in the batch file** (`*.batch.json`, `packages/schema/src/batch.ts`, JSON Schema `batch.json`): `slots: { <name>: "<clipId>.props.<dot.path>" | "<clipId>.asset" }`, `rows: [{ id, ...values }]` with ids `[a-z0-9-]`, unique, used as file names, and optional `formats`, `preset`, `quality`. A slot a row leaves out keeps the template's value. Once #466 typed props ship, slot names may default to prop names.
3. **In-memory variants.** Each row's timeline exists only in memory. A props value is written at its path over the clip's props (missing objects created, arrays indexed by number) and applied through the engine's `clip.set` (`TimelineService.applyInMemory`), so the adapter's schema checks it. Nothing is written under `timelines/`, journaled or proposed.
4. **One row at a time** into the general queue as ordinary `render` jobs; no new job kind and no parallel rows in v1. The next row is queued from the job watcher when the last job of the row before ends, so the queue never goes idle between rows (the daemon's idle exit sees it busy), and `gc` treats a project with a running batch as busy.
5. **Asset swap** keeps the clip's in, out and placement and is never retimed. The row fails when the new file lacks the stream the track plays or ends before `out` (with the slack the engine gives a requested out). The file is probed through the same `TimelineService.source` every placing operation uses. Swapped assets reach the ADR 0026 provenance warnings like any placed asset: each entry carries them.
6. **Per-language voiceover:** a row swaps the voiceover asset; when a subtitle track follows that clip's track, the new asset must have a transcript, else the row fails naming it. Batch never calls `voiceover.generate`, so it never spends money. Per-line placement waits for ADR 0034 slice 4 (built: see "Per-row voiceover and CSV rows").
7. **JSON only** in v1; CSV later (built: see "Per-row voiceover and CSV rows").
8. **Bad rows** fail the whole call with InvalidOperation and data `{ op: "batch.render", row, slot, reason }`; errors of the render check keep their code and gain `row`. No new error code.
9. **No gc roots** for the clip renders of done rows in v1: they are regenerable.
10. **Manifest** at `<out>/manifest.json` (default out `<project>/exports/<batch file name>/`): per row × format `status`, `output`, `job`, `error`, `startedAt`, `finishedAt`, `duration`, `warnings`, plus the batch's `state` (`running` left behind means the daemon stopped mid-batch). Written atomically on each job state change. `batch.render` is mutating (idempotency replay like every mutating method), validates every row × format first, queues the first row and returns with the manifest path. Formats come from `frameshell.json` on disk (ADR 0019 §5), never a pending config proposal.

Outputs are `<out>/<row>.<container>`, with `-<format>` before the extension when the batch lists formats (the `render --formats` rule). `ExportService.planRender` is `render` up to the queue: it takes an in-memory timeline and a path stem, and its `start` queues synchronously; `render` is `planRender(...).start()`, so its params and outputs are unchanged.

## Limits in v1

- Slots reach only top-level clips of the template: not clips inside nested timelines, multicam angles, `elements` or per-format props.
- A second `batch.render` into the same `out` (compared after symlinks resolve) while one runs is refused, and so is a batch whose rows would write one output twice (row `a` in format `web-1x1` and row `a-web` in `1x1`).
- Props paths and slot names may not use `__proto__`, `prototype` or `constructor`.
- An asset swap does not rewrite the `phrases` of a subtitle track that follows the clip: they keep the template asset's word ids, so the new asset's words fall back to the style's grouping.
- ~~No call cancels a whole batch~~ and ~~the manifest holds no hash of the data~~ and ~~slot names are not checked against declared props~~: built, see "Row hash, declared props and cancel".
- Variant clip renders are cache entries no timeline keys, so `gc` removes them once no batch runs; a re-run renders them again.

## Re-runs (slice 3, as built)

`batch.render` takes `rows`, `failed` and `force` beside `file`, `out`, `formats` and `dryRun`; the CLI flags are `--rows`, `--failed`, `--force`.

- **Choosing.** `rows` is a list of row ids or `first..last` ranges (both ends in, the file's order; ids never hold `.`); the call fails with InvalidOperation `{ row, reason: "unknown row", field: "rows" }` for an id the file lacks and for a reversed range. `failed` keeps the chosen rows (default every row) that have no manifest entry yet or an entry that is not `done`. It reads `<out>/manifest.json` and is refused (InvalidOperation, `field: "failed"`) when there is none, it is not a valid manifest or it names another batch file; a plain run ignores such a manifest.
- **Skipping.** A chosen row is skipped, and listed in the result's `skipped`, when the manifest has a `done` entry for each output the row would write and every file exists and its data is unchanged (slice 6: the entry's `hash`); `force` renders it anyway. A row whose file was deleted renders again.
- **Only chosen rows are planned.** The rows a call does not render are neither validated nor compiled, so a bad row elsewhere does not block re-running one failed row. A skipped row is still planned, to learn its outputs before comparing them with the manifest, and its outputs count in the clash check; the entries of rows left alone count too.
- **Manifest merge.** The new manifest holds every row of the file that has entries, in file order: freshly queued entries for the rendered rows, the earlier ones for the rest. Entries of rows the file no longer has are dropped. An earlier entry left `queued`, `running` or `planned` by a stopped daemon is rewritten as `canceled` with the error "The daemon stopped before this render ended." in the rows the call leaves alone (`failed` picks it up like any not-done entry); `state` is `done` once every entry this run queued ended. A call with nothing left to render queues no job, writes no manifest and returns the existing entries; `preset` is null when no row was chosen.
- **Wire.** Protocol 119: params `rows`, `failed`, `force`; result `skipped`, and `preset` nullable. The CLI waits only for the renders the call queued and exits 1 only if one of those failed.

## Slot defaults and the review column (slice 5, as built)

- **Slot defaults.** Typed props (ADR 0033 slice 2, #466) are the `data-composition-variables` of a HyperFrames composition, which only the plugin reads, and core checks props through the adapter's `propsSchema` alone. So the default is a spelling, not a lookup: a slot value `<clipId>.props` with no path sets the prop named like the slot, `{ "title": "c_8f2a1b.props" }` meaning `c_8f2a1b.props.title`. `parseSlotTarget(slot, name)` takes the slot's name for that form; the explicit path forms are unchanged, and a slot name is already barred from `__proto__`, `prototype` and `constructor`. Checking slot names against a composition's declared variables, or exposing every declared prop at once, would need the adapter to say what it declares (a `plugin-api` addition) and is left for when a template author asks for it.
- **Review column.** `batch.render` takes `review` (CLI `--review`, off by default: a review decodes the whole file). When a row's render job ends `done`, `ReviewService.run` reviews the file (`sheets: ["metrics"]`, `view: "current"`, so no sheet images are written), one review at a time in order, while the next row renders. The entry's new `review` is `{ state: pending | done | error, verdict: pass | warn | fail | null, warnings, failed, checks, run, error }`, null when not asked or when the render did not end `done`. `failed` is `metrics.requirements.failed` (0 without a `requirements.json`), `warnings` the length of `metrics.craft` (waived warnings are not in it), `verdict` is `fail` when `failed > 0`, else `warn` when `warnings > 0`, else `pass`, and `run` names `.frameshell/review/<run>/`, whose `metrics.json` holds the detail (only the last 10 runs are kept, as for any review, so a batch of more rows loses the oldest).
- **Lifecycle.** The batch ends, and the manifest says `done`, only after the last review ended; `gc` keeps clip renders until then, and a second batch into the same `out` is refused meanwhile. A review that throws (no ffmpeg) becomes `state: "error"` with the first line of the message: the render stays `done`. Rows skipped as done are reviewed when their entry has no `done` review and the file exists, with no render queued; a run with only such rows queues no job and still returns the manifest. An older manifest has no `review` and reads as null.
- **What it checks.** The review is of the file, as `frameshell review --file` is. The export check (`metrics.delivery`) runs only for a batch without `quality`, against the preset the rows used and, when the batch lists formats, the row's format; it plans the saved template, not the variant (the variant keeps the clip's in, out and placement, so the length is the template's). Requirements about clips (`clip.appearsBy`...) are skipped on a file, as for `review --file`.
- **CLI.** `--review` waits for the manifest to say `done` (the reviews finish after the render jobs, so the CLI reads the manifest the daemon writes), prints `review: <verdict> (<n> warnings: <checks>), run <n>` under each file and exits 1 when a render failed or a verdict is `fail`.
- **Wire.** Protocol 144: param `review`; `BatchEntry.review` (nullable, default null).

## Per-row voiceover and CSV rows (slice 5, as built)

- **`voiceover` slot.** A slot written `voiceover` (the target names no clip) holds the row's voiceover: the project-relative path of a voiceover script (ADR 0034), or `{ script, lines, at, tempo, start, gap, track, replace }`, the arguments of `voiceover.place` that make sense per row (the timeline is the template; `dryRun` has none). A file may have one such slot. `BatchVoiceoverSchema` is the object form; time values are seconds or any TimeRef string, resolved by the shared resolver (`resolveTimeRefAsync`, markers, `beat:`, `bar:` of the row's own variant), never parsed here.
- **Placed, not twinned.** After every other slot (so the voice meets the row's final timeline), `placeRowVoiceover` (`packages/core/src/batch/voiceover.ts`) runs `planVoiceoverPlacement` on the in-memory variant and writes the plan with `runVoiceoverPlan`, each step applied through `TimelineService.applyInMemory`: the same phrase clips, spacing, anchors, tempo, 12 ms fades, positional line ids and overlap rules as `voiceover.place`, with nothing written, journaled or proposed. It never generates (decision 6 stands: a line with no take fails the row naming it) and so never spends. A voiceover that places no phrase fails the row.
- **Subtitles and length.** When a subtitle track follows the voice track the plan uses, every take it places needs a transcript, else the row fails naming the take (`reason: "no transcript"`, as for an asset swap). Placed phrases can run past the template, and the export is as long as its longest clip, so the row's warnings (the manifest entry's too) say `The voiceover makes the video X s long, Y s longer than the template's Z s`; the picture is never retimed (decision 5).
- **Errors.** Every refusal of the planner (`ScriptNotFound`, an unknown line, an `at` key or marker that does not resolve, overlap, clips already playing the takes without `replace`) becomes InvalidOperation with `{ op: "batch.render", row, slot, reason, field? }` (decision 8), the message without the `voiceover.place:` prefix. The template's own clips on the voice track are not touched unless `replace` names clips that play the same takes; new phrases start after them.
- **CSV rows.** A batch file gives `rows` or `csv` (the name of a CSV file relative to the batch file's folder), never both. `rowsFromCsv` (`packages/core/src/batch/csv.ts`) reads RFC 4180 (quoted cells with the delimiter, doubled quotes and line breaks; CRLF; a BOM; blank lines skipped) with the delimiter the header line uses most (comma, `;` or tab). The header is `id` and slot names; a slot with no column keeps the template's value for every row, an empty cell leaves that slot to the template for that row. Cells are typed by the slot: a props slot takes the type of the value the template clip holds at that path (`templateColumnTypes`: string, number, boolean, else JSON), a path the template lacks is text, and a header `name:type` (`text`, `number`, `boolean`, `json`) overrides either. Asset and voiceover cells are text. The result is checked by the same `batchRowIssues` as rows in the file (ids unique, slots declared, voiceover valid). Every problem is collected with its line and column (`line 4, column price: expected a number, got "x"`, header problems at line 1, the first 20 listed and the rest counted) in one InvalidProjectFile; a missing CSV file is AssetNotFound. Reading happens on every call, after the template loads, so a re-run sees an edited CSV (the manifest still holds no hash: `force` after editing).
- **Not here.** A row naming a slot of nested timelines or a `voiceover` per format; generating the takes from the CSV (paid generation stays with `voiceover.generate`); one script per row replaced by text in the row (the script is a file, so its lines are reviewed and versioned like any script).
- **Wire.** Protocol 154: the batch file accepts the new slot and `csv` (daemon-side, so an older daemon rejects them); `batch.render` params and result are unchanged, its description says so. JSON Schema `batch.json` regenerated.

## Row hash, declared props and cancel (slice 6, as built)

Owner decision 2026-11-17 (Q3 of #477): all three.

- **Row hash.** Each manifest entry has `hash`: SHA-256 (32 hex digits) of the canonical JSON (`canonicalJson` of the clip render key, one serializer) of `{ row, slots, template }`: the row's resolved cells (CSV rows are typed first, so a changed cell or column type shows), the batch file's `slots`, and the template timeline's content without its `revision` (a save that changes nothing keeps the hash). It is the same for every format of a row. A chosen row whose planned entries are all `done` with the files in place is skipped when every earlier hash equals the new one; when one differs it renders again with no `force` and the row is listed in the result's new `changed` (the CLI prints it, the dry run too). An entry with no hash (a manifest from before slice 6, schema default `null`) counts as unchanged, so old manifests behave as before. `force` renders everything and reports no `changed`. Not hashed: the bytes of a swapped file edited in place under the same name, `preset`, `quality`, `formats` (formats change the output names, so those rows have no earlier entry), nested timelines the template plays: `force` covers them. Protocol 168: `BatchEntry.hash`, result `changed`.
- **Slot names against declared props.** The optional plugin-API hook `ClipAdapter.declaredProps(clip)` returns the top-level props the clip's composition declares, or `null` (an empty list counts as null) when it declares none; a throw counts as null. `TimelineService.declaredProps` looks the adapter up and `rowVariant` checks the first segment of a props slot's path before applying it: a name not declared is InvalidOperation with data `{ op: "batch.render", row, slot, reason: "unknown prop", prop, declared }`, in `--dry-run` and in the render alike. HyperFrames answers from the `id`s of the entry HTML's `data-composition-variables` array (an object, bad JSON or an empty array declares nothing, as the producer ignores them). Adapters without the hook (Remotion, Blender: its schema already refuses unknown props) keep today's behaviour, as the owner decided.
- **`batch.cancel { file, out? }`.** Mutating, replay-keyed like every mutating method. It finds the running batch by the canonical `out` (default `<project>/exports/<batch name>/`) and refuses with InvalidOperation `no batch running` or `other batch` (another batch file renders there). It sets the run canceled: no further row is queued, the entries of rows not started become `canceled` with no job, reviews still waiting are dropped (a running one finishes), and the render jobs of the row in progress are canceled through `JobQueue.cancel` (a queued one ends at once, a running one aborts its ffmpeg and ends `canceled`). The manifest's `state` gains `canceled`, written once the last job ended; the call waits for it up to 10 s and returns `{ dir, file, out, manifest, state, canceled, entries }`, with `state: "running"` when the render had not stopped yet. Rows already `done` keep their files and entries; `--failed` re-runs canceled ones like any entry that is not `done`. A second call finds nothing running.
- **CLI.** `frameshell batch cancel <file> [--out dir]`. Ctrl-C in a running `frameshell batch` asks the daemon the same (once; a second Ctrl-C ends the CLI as usual), and the CLI also stops waiting when another process cancels: it polls the manifest for `canceled`, since the rows never queued have no job to wait for. Both exit 1 and print the rows not rendered.
- **Wire.** Protocol 168: new method `batch.cancel`; `BatchEntry.hash`; `BatchManifest.state` `canceled`; `batch.render` result `changed`. The skill (`batch.md`) and `docs/mcp.md` list `yes` and `batch_cancel`.
- **Still out.** Parallel rows (a flag if real batches show idle cores), slots into nested timelines, `elements` and per-format props, rewriting the `phrases` of a subtitle track after an asset swap.

## Rejected

- **A timeline file per row** (option B): watcher, background renders, journal entries and one review-mode proposal per row, and cleanup left to the person.
- **A project copy per row** (C): duplicated media or links, cold caches, per-project plugin trust.
- **Clip-only batch** (D): no footage, sound or subtitles per row, and a second export path; a one-clip timeline covers it.
