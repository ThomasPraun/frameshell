# Blender clips: an official adapter renders a `.blend` range with the person's own Blender into the clip cache

#482 (epic #451, step 6 "3D and story shorts") asks for a clip type `blender`. An official plugin `plugins/blender` (`@frameshell/blender`) renders a frame range of a `.blend` file in the project with the person's own Blender, encodes the frames with the managed ffmpeg to VP9 with alpha (the ADR 0002 file format, so preview and export need nothing new), and caches the result like any generated clip. Blender is never downloaded, bundled or redistributed. The owner decided option A on 2026-11-10 (the ten points below, from the ticket's decision comment). Slice 1 of #482 implements the core lookup and a minimal draft-only adapter. Slice 2 adds Cycles finals on the draft/final model the owner set for every generated clip on #501 (ADR 0041 decision 11), which replaced this ADR's `quality` prop: decision 4 and 8 below are amended, each with what was built. Slice 3 adds the agent playbook and the `clip.compare` look sheet. Slice 4 time-remaps a scene at another frame rate (decision 7 amended), allows files outside the project with a warning (owner, 2026-11-16) and finds Blender at its standard install paths (decision 2). Slice 6 renders only the clip's window and keys on its start and end (decision 7 and "Left open" amended). **Evidence** below was measured with Blender 5.2.3 LTS on macOS; 4.5 LTS, Linux, Windows and finals are still open.

## Context

- Blender is GPL (GPL-3.0-or-later binaries, GPL-2.0-or-later source; blender.org/about/license) and about 300 MB. macOS ships it only as a `.dmg`, which the binary manager cannot extract (tar and zip only). The person usually has their own Blender already, because the agent edits the `.blend` through a Blender MCP while Frameshell only renders; a second, different Blender version saving the same file risks version-mismatch saves.
- #478 (decided 2026-11-10): never depend on an external tool's CLI for what core does. Blender has no in-process alternative, so a subprocess is the only route; every encode and probe still goes through the managed ffmpeg.
- The plugin API already supports what is needed (`ClipAdapter.render`, `RenderContext.ensureBinary`, `progress`, `signal`), except that `inputs(clip)` has no host services: the adapter cannot ask where Blender is, so it cannot put the Blender version or a `.blend` dependency listing into the key.
- `BinaryManager.#packageOf` threw `Unknown binary` for any tool not in the manifest, so `binaries.blender` could not work before Blender had a manifest entry. A package may have no builds (`ensure` then throws `BinaryUnavailable`) and `onDemand` keeps `doctor` from listing it as a problem.
- The clip queue has concurrency 1 (`daemon.ts`), which already means one GPU render at a time, and also that a long Blender render holds back every other generated clip and export.
- Cycles cannot draw offscreen; drafts use EEVEE or Workbench. bpy changes between releases: Principled BSDF sockets were renamed in 4.0, the EEVEE id is `BLENDER_EEVEE_NEXT` in 4.2-4.x (and `BLENDER_EEVEE` again from 5.0), `Action.fcurves` went away in 5.0.

## Decision

1. **Official plugin in this repo.** SPEC §13 ("official plugins limited to two") is amended once, to the plugins that ship today (`whisper-cpp`, `hyperframes`, `remotion`), Blender and `packages/motion` (ADR 0033). Anything else goes to a community plugin.
2. **The person's own Blender install**, never a managed download. Core gets a `blender` package in the manifest with no builds, `onDemand`, a `--version` probe and a `userInstall` description; `binaries.blender` (project or global) names the executable. `ensure` without an override fails with a message that says Blender is the person's own, which versions work, where to get it and the exact `binaries` line to add (not "no managed build"). `doctor` shows the version, says `not installed, set binaries.blender` in the CLI when there is none, and reports a problem only when a Blender that runs is out of range or an override points at nothing.
   **As built (slice 4): standard paths.** With no `binaries.blender`, core looks where Blender's installers put it. The rules are data on the package (`UserInstall.standardPaths`, per platform family: a fixed `file`, a name on `path`, or `versioned` folders with the newest supported version first), read by one generic lookup in `BinaryManager.locate` (`findUserInstall`), so `doctor`, `ensure` and every key check agree; nothing in the manager names Blender. macOS: `/Applications/Blender.app/Contents/MacOS/Blender`, then `blender` on PATH. Windows: `%ProgramFiles%\Blender Foundation\Blender <x.y>\blender.exe`, newest folder in the supported range (else the newest, so `doctor` reports it as out of range rather than missing), then `blender.exe` on PATH. Linux: `blender` on PATH, then `/snap/bin/blender`. Nothing runs while looking (the version probe stays the adapter's and `doctor`'s). A found install is `source: "system"` with `found: "standard" | "path"` in `BinaryLocation` and in `doctor`'s `BinaryReport` (protocol 161); the CLI prints `system (found at its standard install path)` or `system (found on PATH)`. A `binaries.blender` override, project or global, always wins. `BinaryManagerOptions.env` (PATH, `ProgramFiles`) and `standardPaths: false` exist for tests. PATH lookup reuses `findOnPath` (`binaries/command-runner.ts`, also behind `runCommand`).
3. **Supported range: the 4.5 LTS and every 5.x** (5.2 is the current LTS; only 5.2.3 has run, 4.5 stays supported but untested), checked at the start of every key check and render, with a message naming the version, the range and `binaries.blender`. `supports` in the core manifest (for `doctor`) and `supportedBlender` in the plugin repeat the rule; a parity test checks they agree on every tested version.
4. **Draft by default; final only when asked.** A final estimated over 5 minutes asks for confirmation, and export warns when it contains draft renders. *Amended 2026-11-11 (owner, on #501):* not a `quality` clip prop but the shared draft/final model of ADR 0041 decision 11: each Blender clip keeps two cached renders, the EEVEE or Workbench draft for the preview and draft exports, the Cycles final for final and untiered exports, which wait for it.
   **As built (slice 2):**
   - **Plugin API, additive** (`apiVersion` stays "1"): `ClipAdapter.finals = { estimate(clip, { projectDir, fps, width, height }) }` declares an adapter that renders finals; `RenderContext.tier` (`"draft"` or `"final"`) tells its `render` which one, and is absent for other adapters. A host older than this passes no tier, and the adapter then renders the draft as before.
   - **Keys:** the draft keeps the key it had (no new field), so existing Blender renders stay valid; the final's key adds `final: true` (`clipCacheKey`). `CACHE_LAYOUT_VERSION` unchanged. `gc` keeps both, as for motion blur.
   - **When the final renders:** never in the background. `ClipRenderer` queues it only when `ensure` runs with `tier: "final"` and `waitForFinals` (the export job of a `render` with `quality: "final"` or no quality); `clip.renders` reports it as `final` with `onDemand: true`, `waiting` until then (Chat about this never holds its frame for it); once cached, the preview plays it as it plays a blurred render. `frame` and `review` (which call `ensure` without `waitForFinals`) use the final when it is cached, else the draft with a warning: a still never starts a half-hour render. A clip whose adapter has both finals and motion blur gets one final, blurred and with `tier: "final"`.
   - **Confirm:** `render` and `batch.render` (not `planRender`: the review's delivery check and a batch `dryRun` only compile) sum the estimates of the finals the export would make (missing, not running, every format rendered; for a batch, every chosen row, before the first row queues). Over 300 s, or any estimate unknown (the adapter threw), they fail with `ConfirmationRequired` before queueing anything: `data = { finals: [{ clip, type, format, seconds, row? }], seconds, limit: 300, hint }` (`row` for a batch). `yes: true` on either (CLI `render --yes`, `batch --yes`) is the person's agreement; that is the existing confirm pattern of `voiceover.generate`, without a token because nothing is charged. Cached finals never ask again. The sum counts a final once per format and per row even when they share one cache key, so it can only over-estimate.
   - **Estimate:** frames x megapixels x seconds per frame and megapixel, plus 10 s for start-up and encode. The rate is the last measured for that `.blend` on this machine, else the project's last, else 5 s (the #482 note measured about 4.5 s on an M4 Pro: 6-7 s a frame at 1600x900, 80 samples). Every final of two frames or more records in `.frameshell/blender/finals.json` (never a key input) the seconds `render.py` reports per frame, leaving out the first frame: that one also pays for scene sync and, on the first Cycles final on a Mac, Blender's Metal kernel compile (Evidence), which the estimate does not count.
   - **Draft warning:** a `render` with `quality: "draft"` adds `Clip <id> (blender) is exported from its draft render, not its final one: ...` per clip and format to its `warnings`; a final export has none.
   - **Props:** `quality` is refused with how to choose draft or final at export (decision 8).
   - Protocol 152 (`render.yes`, `batch.render.yes`, the `ConfirmationRequired` data of both, `final.onDemand` in `clip.renders`, descriptions); no schema change.
5. **No hard render cap:** progress and cancel (the render kills Blender on `signal`), plus the confirm in 4.
6. **One clip queue in v1:** a long final blocks other renders and exports; a second queue or priorities get their own ticket. Built in #502: one queue still, with two priorities (`JobQueue`, `packages/core/src/jobs/queue.ts`): renders somebody waits for (`clip.renders`, export, frames) start before background refresh renders, which still get a slot after four interactive starts in a row. A second lane was not needed: it would let two renders run at once, which Blender and headless Chrome should not. A running render is never preempted; `job.cancel` stops one.
7. **Scene fps different from the project fps is refused** with a fix-it message (`Set the scene's frame rate to N … frames are never remapped`) until a time remap exists. The check runs inside Blender (`render.py`), before any frame renders. *Amended by slice 4:* the time remap exists, so nothing is refused for its rate.
   **As built (slice 4):** project frame k (composition time k / project fps, from the scene's first frame) shows scene frame `frame_start + k × scene fps / project fps`, set with `scene.frame_set(whole, subframe=fraction)` before each still render; the frame count still comes from the clip's `in + duration` at the project fps (`frameCount`, unchanged). Rates within 0.001 fps of each other count as equal (29.97 typed against 30000/1001). Not Blender's Time Stretching (`frame_map_old` / `frame_map_new`): those are whole numbers up to 900, which cannot hold 24000/1001 against 30 (800/1001) or 24 against 30000/1001 (1001/1250), and they remap from frame 0, not from the scene's start; a subframe holds any ratio, so **no ratio is refused** and the fix-it refusal of this decision is gone. A clip that runs past the scene's End frame is still refused, naming the scene frames it needs and both rates. The remap ratio is in the key already: it is a function of the scene rate, which the `.blend`'s bytes carry (an input), and of the project fps, which the host's key carries (`format.fps`); no extra marker. Each `frame` event now reports the `sceneFrame` it showed. Limits: image sequences, movie textures and baked caches inside the scene hold their nearest whole frame at a subframe; whether `bpy.ops.render.render` honours the subframe on 4.5 and 5.x is **not verified** (no Blender on the machine that built slice 4): the opt-in real test checks it (a 24 fps dot at scene frame 5.8 must sit at 88 px, not the 80 px of frame 5).
8. **Props: `scene`, `camera`, `quality`, and nothing else.** *Amended with decision 4:* `scene` and `camera` only; `quality` is refused with a fix-it message. No agent Python reaches Blender; the plugin runs only its own scripts with a JSON request. The `.blend` is the clip's `source` (as for the other adapters, and the one the job and `clip add --source` already name), so the props schema refuses a `file` prop and says so. There are no `frameStart`/`frameEnd` props: the frame range comes from the clip (below).
9. **`render.py` (bpy) is Apache-2.0**, which is compatible with GPL-3.0 as blender.org asks of published bpy scripts. That is our reading, not legal advice. The plugin README says so, and every shipped script carries the SPDX header.
10. **The device (GPU or CPU) is not in the cache key.** The cache is local.

From the review of the draft:

- **The Blender version is probed per key check and is part of the key.** The adapter asks `blender --version` (cached by the executable's size and mtime, so an upgrade is seen at once) and returns `.frameshell/blender/version/<version>.json` from `inputs()`. An upgrade changes the path and so the key: every Blender clip re-renders. The version is deliberately not stored in the per-`.blend` dependency cache, which would go stale on an upgrade.
- **The frame range is the clip's own.** Composition time 0 is the scene's first frame (`frame_start`); the render covers frames up to `in + duration` at the project fps (each shown at its time on the scene's clock since slice 4, decision 7), so file time t shows composition time t as the adapter contract requires. A clip longer than the scene is refused with the scene's end frame. Because the host's key ignores placement (`type`, `source`, `props`, `elements`, inputs, format), the part rendered travels as an input file, `.frameshell/blender/range/<inMs>-<endMs>ms.json` (slice 6; before it `<endMs>ms.json`, named by `in + duration` in milliseconds): changing `in` or `duration` re-renders a Blender clip, unlike other adapters. That is the price of rendering only what the clip plays instead of the whole scene. **Amended in slice 6:** the render covers just `[in, in + duration)`, with the start padded by transparent frames (see Slice 6 below).
- **The watcher debounce stays the host's** (200 ms after the last file event). A `.blend` that is not a finished Blender file (empty, or no Blender magic bytes: `BLENDER`, gzip or zstd) is refused with "not a finished Blender file (it may still be saving)", which keeps the clip without a key until the next change. `.blend1` backups are never inputs.
- **Every run is `blender -b --factory-startup -Y <file> --python-exit-code 1 -P script -- <json>`:** no user add-ons or preferences, scripts embedded in the file never auto-run, no socket, a non-zero exit when the script raises (Blender exits 0 otherwise). Frame count is checked after the run.

## Plugin API: `inputs(clip, context?)`

`ClipAdapter.inputs` gets an optional second argument, `InputsContext { projectDir, ensureBinary, signal? }` (`signal` since slice 5; typed optional, `signal?: AbortSignal | undefined`, since a host older than slice 5 passes none, #471; still `PLUGIN_API_VERSION` `"1"`), passed by `ClipRenderer` on every key check. Additive (like `refreshRenders`, ADR 0009): `PLUGIN_API_VERSION` stays `"1"`, existing adapters ignore it, and an adapter that needs it fails with "this Frameshell is too old" when it is absent. No protocol or schema change, no `PROTOCOL_VERSION` bump, no `gen:json-schema`.

## Design

- **Final (slice 2):** with `quality: "final"` in the request (the host asked for `tier: "final"`), `render.py` uses Cycles: 80 samples, adaptive threshold 0.02, OpenImageDenoise, seed 0 and no animated seed (a rerun draws the same noise), 6 bounces, reflective and refractive caustics off, persistent data. The device is the first GPU backend Cycles finds (`OPTIX`, `CUDA`, `HIP`, `METAL`, `ONEAPI`) with every device of that kind on, else the CPU, picked by the script because `--factory-startup` leaves Cycles on the CPU; the `start` event names it. Everything else (scene, camera, fps and range checks, transparent film, PNG, stamps off, the encode) is the draft's. Progress says `Rendering the final (Cycles)`.
- **Render:** `render.py` picks the scene (`props.scene` or the file's), works out the time remap (decision 7), sets the camera (`props.camera` or the scene's active one), resolution at 100 % of the project size, `film_transparent`, PNG RGBA 8 bit, EEVEE (`BLENDER_EEVEE_NEXT` or `BLENDER_EEVEE`, found by trying; else Workbench) at 16 samples, then renders frame by frame to `frame_%06d.png` in a temp directory. Burn-in and PNG metadata stamps are switched off (they hold the date and render time, so a rerun would differ). It prints `FRAMESHELL <json>` lines (`start`, `frame`, structured `error`) the adapter parses for progress (0 to 0.9; the encode takes the rest); Blender's own `Fra:` lines are read too, though 5.2 prints none in background renders.
- **Encode:** the managed ffmpeg, `libvpx-vp9 -pix_fmt yuva420p -auto-alt-ref 0 -b:v 0 -crf 20 -row-mt 1 -threads N -deadline good -cpu-used 4` (the ADR 0009 speed flags and alpha settings; `-crf 20` is this adapter's own choice, not measured against Remotion's default; `bitexact` keeps the muxer's random UIDs out), `-an`. The PNG sequence goes in at the project fps, NTSC rates (29.97, 23.976, 59.94) as the exact fraction (`30000/1001`). Result `{ file, hasAlpha: true }`. Frames on disk also leave room for a ProRes master later (ADR 0002 reserve).
- **Inputs:** the `.blend`; the version file; the range file; `.frameshell/blender/<blend hash>-<path hash>/deps.json`; and every in-project file from `bpy.utils.blend_paths(absolute=True, packed=False, local=False)` (libraries, images, caches). The listing runs Blender once per `.blend` content and project path and is read from `deps.json` afterwards, also after a daemon restart; relative links resolve against where the `.blend` sits, so the project path is part of the cache, and part of the listing file's name: identical copies at two paths each have their own file. Files outside the project: see below. The listing has a 5 minute timeout, and since slice 5 the host's stop signal (`InputsContext.signal`) kills it like a render's cancel, so stopping the daemon leaves no Blender running.
- **Files outside the project (slice 4, owner decision 2026-11-16: allowed, with a warning):** `deps.py` lists them as it always did (`blend_paths(absolute=True, packed=False, local=False)`); `outsideProject` keeps them as absolute paths, in memory only. Their content hashes (SHA-256, first 16 hex digits, cached by size and mtime; a missing file or a folder counts as `missing`) go, in path order but with no path, into `.frameshell/blender/<blend hash>-<path hash>/outside.json`, a key input beside `deps.json`: an edit, or a missing file appearing, changes the key. `deps.json` now holds `outside: <count>` instead of the paths, so absolute paths never land in a project file; a `.blend` with outside files is listed again once per daemon run (one Blender start, about 0.6 s on the small file), and a `deps.json` written before slice 4 (no count) is listed again once. Nothing watches outside files: an edit re-renders when the clip's key is next checked (export, `clip renders`, a refresh for an edit inside the project). Every render of such a clip calls `RenderContext.warn` with `blender clip <id>: <source> loads N files from outside the project (<paths, at most 5>); their content is in the render key, but Frameshell does not watch them: ...`, kept with the cached render (per machine, under `.frameshell/cache/`). Every run keeps `--factory-startup -Y`. **Drivers inside a linked library outside the project under `-Y`: not verified** (no Blender on the machine that built slice 4). `-Y` sets the process-wide auto-exec flag, and Blender evaluates linked data under the same flag, so they are expected to stay off like the file's own; the opt-in real test links a library whose object has a scripted driver that writes a file, renders, and checks the file is absent.
- **Cancel:** `signal` sends SIGTERM to Blender's whole process group (`taskkill /T /F` on Windows) and SIGKILL to the group five seconds later, so a launcher script (snap, flatpak, a shell wrapper) as `binaries.blender` does not leave Blender running.
- **Camera:** `props.camera` must be an object of the chosen scene; the error lists that scene's cameras.
- **Left open (not decided here):** `.frameshell/blender/` (one listing per saved `.blend`, one range file per distinct length, version files) was not cleaned by `gc` until slice 5 (see below); and keying on `in + duration` re-renders on any trim, including a shorter end the old render already covers (SPEC §6.5 documents the exception to "placement never re-renders"). **Decided (owner, 2026-11-17, #482 Q5):** a head trim re-renders too, so the key is the window's start and end. A shorter end still re-renders; bucketing the length or keying on the scene's `frame_end` stays rejected.

## Evidence

Measured 2026-11-10 on an Apple M3 MacBook (8 cores CPU, 10 GPU cores, 8 GB), macOS 26.3, **Blender 5.2.3 LTS** (build 2026-10-22, `/Applications/Blender.app/Contents/MacOS/Blender`), managed ffmpeg. Every run was headless from a terminal process (`-b --factory-startup -Y`, no window). Scenes were built by a bpy script per run (`--factory-startup`, nothing committed): an ortho camera, a white emission panel mixed 0.6 with Transparent BSDF, an opaque red emission dot, nothing in the corners. `FRAMESHELL_TEST_BLENDER=/Applications/Blender.app/Contents/MacOS/Blender pnpm exec vitest run plugins/blender` passes (37 tests). **Blender 4.5 LTS was not tested** (not installed): it stays in the supported range on the strength of the 4.2-4.x code path (`BLENDER_EEVEE_NEXT`), unverified. Linux, Windows, finals (Cycles), Chromium playback and linked `.blend` libraries were not tested either.

## Considered options

- **A. Official plugin, the person's Blender, frames encoded by the managed ffmpeg. Chosen.**
- **B. Same adapter, managed Blender download.** Rejected: dmg extraction on macOS, about 300 MB per platform, re-pins per release, a mirror would redistribute GPL binaries, and a second Blender version could save the person's `.blend`. The reproducibility it buys is not needed because the cache is local.
- **C. Skill playbook only; the agent renders and imports the result as media.** Rejected as the main path: no cache key, the clip is not linked to its `.blend`, and renders would land in `assets/`, which is precious data. It remains what an agent can do today (SPEC §6.3 imports VP9 alpha).
- **D. Community plugin plus a generic user-tool hook in core.** Rejected: a plugin manifest change for one consumer, and the quality and security of the Blender integration would leave the repo. The generic part is the `userInstall` package field, which another external tool can use.
- **Let `ensureBinary` resolve an override for a tool no package ships.** Not done: `locate` still throws `Unknown binary` for names outside the manifest. Blender works because it now has a package; a plugin cannot invent tools.
- **Find Blender in standard install paths when no override is set.** Not in slice 1: `doctor` and `ensureBinary` must agree on one answer, so it belongs in core with the other lookup. Built in slice 4, in core, as generic package data (decision 2). Rejected there: a lookup inside the plugin (`doctor` would not see it), and running each candidate's `--version` while looking (a slow start for every key check).

## Consequences

- **Core:** `BLENDER_PACKAGE` and `BLENDER_TOOL` in `packages/core/src/binaries/manifest.ts`, `BinaryPackage.userInstall`, `ensure` and `doctor` behaviour as in decision 2 and 3, the CLI doctor text. `OFFICIAL_ADAPTERS` (`plugins/host.ts`) names `@frameshell/blender` in the install hint.
- **Plugin API:** `InputsContext` as above.
- **New plugin** `plugins/blender` (`@frameshell/blender` 0.1.0): manifest, adapter, `python/render.py`, `python/deps.py`, a skill stub, README with the licence note; registered in the root `tsconfig.json`, the release workflow's plugin build and the npm plugin checks. The npm Trusted Publisher for the new package must be set up by the owner before its first release (`docs/release.md`).
- **Docs:** SPEC decision 40, §6.5, §8.2, §9, §12 and §13 (the scope risk amended once, a risk row for bpy churn and the shared queue), `docs/binaries.md` "Blender (your own install)", GLOSSARY, CHANGELOG, CLAUDE.md doc map.
- **No** `PROTOCOL_VERSION` bump, Zod model change, `gen:json-schema` or daemon method; `CACHE_LAYOUT_VERSION` unchanged. The skill of the core agent guide (`skills/frameshell/`) is untouched: the plugin ships its own.
- **Slice 3 (as built): the playbook and the look sheet.** `plugins/blender/skills/blender/SKILL.md` is now the agent playbook: which route (Blender clip, the `hyperframes` three.js templates, imported media), how to prepare a `.blend` (frame rate, scene length from the scene's first frame, camera, size taken from the project, transparent film so the World never shows, blended materials for partial alpha, files inside the project, no add-ons or Python under `--factory-startup -Y`, one scene per lighting setup), the look recipe from the #482 research, draft to final with the 5-minute confirmation, and a failure-and-fix table that quotes the messages of `describeRefusal`, `VersionProbe` and `deps.ts`. The look sheet is a core command, not a Blender one: **`clip.compare`** (`frameshell clip compare`, MCP `clip_compare`; protocol 156) renders one frame of any generated clip under up to 11 variants (`props` merged over the clip's own, a `null` value drops a key, and/or another project `source`) beside the clip as it is, as one labelled PNG in `.frameshell/looks/`. It is the `grade.compare` design applied to generated clips: each tile is `ExportService.frame` on a copy of the loaded timeline whose clip carries that variant, tiled by `writeSheet` (the `review` sheet writer, no second tiler), with `columnsFor`, `evenHeight` and the frame pick (`compareFrame`) shared with `grade.compare`. For a Blender clip a variant is a scene (`props.scene`, one scene per lighting setup in one `.blend`), a camera (`props.camera`) or a copy of the file. Each variant is rendered by the normal clip queue (a draft for Blender: EEVEE, or Workbench, never a final, as for every `frame`), so the first sheet costs the drafts it has not got cached and a repeat is instant; the render runs from the scene's first frame to the frame shown, so a look sheet belongs on a short clip. It never touches the timeline; each tile's `flags` are the `clip set --props` that keeps it (a different `source` has no flag). It is generic on purpose: the same call compares prop variants of a `hyperframes` or `remotion` clip, and a media clip's colour stays with `grade.compare`. The sheet shows drafts: EEVEE and Cycles differ in bounce, soft shadow and glass, so the playbook says to choose the setup on the sheet and confirm it on a final. Rejected: a Blender-only command (the clip queue and sheet path are generic), a skill-only recipe with a scratch timeline and a `review` contact sheet (tiles labelled by time, not by look, and several calls), and extra tiles per camera (one `camera=` look each).
- **Slice 4 (as built):** fps remap (decision 7), files outside the project with a warning (Design), standard paths (decision 2); protocol 161 (`system` source and `found` in `doctor`, and the `clip.compare` description now says a failed variant is `ClipRenderFailed` and that `gc` removes variant renders no timeline uses). - **Slice 5 (as built, #509): `gc` of `.frameshell/blender/` and a stop signal for the listing.** Two additive plugin-API pieces, `PLUGIN_API_VERSION` stays `"1"`, no protocol change (`GcEntry` kind `clip`, only its description says what else it covers), no Zod model change.
  - **`ClipAdapter.gc?(context)`** with `AdapterGcContext { projectDir, inputs, dryRun, keepNewerThan, signal }`, returning `{ path, bytes }[]`. `ClipRenderer.gc` keys every generated clip exactly as it does for the render cache (every timeline, nested ones flattened, every declared format), now keeping the paths each adapter's `inputs()` returned in the same pass (`Keyed.paths`, no second key check), and gives each adapter with a hook the union of its own clips' paths. The hook runs under the same rules as the cache sweep: not when a render or export job runs, not when a timeline cannot be read or a clip has no key (the existing skipped entries say why, nothing is deleted); a hook that throws is one more skipped entry naming the plugin and the other adapters still run. What a hook deletes comes back as `GcEntry` kind `clip`, in the same `{ removed, skipped }` of `ClipRenderer.gc`, so the daemon handler and `dryRun` are unchanged. A project with no generated clips loads no plugin, as before (so its `.frameshell/blender/` stays until a generated clip exists).
  - **Why a hook in the plugin, not core sweeping the folder.** Core would have to know the plugin's layout (`<hash>-<hash>/`, `range/`, `version/`), the twin this ADR avoids with the `userInstall` field; and a generic "delete everything under a state folder that no input names" would delete `finals.json`, which is never an input. The plugin recognises its own entries by name alone (`state-gc.ts`): a listing folder `<16 hex>-<8 hex>/` goes when neither its `deps.json` nor its `outside.json` is an input, `range/<ms>ms.json` and `version/<x.y[.z]>.json` go when not an input; `finals.json`, unknown names and symlinks are never touched.
  - **Grace floor.** `keepNewerThan` is the start of the `gc` minus a minute: whatever was modified at or after it (a listing folder counts its newest file and its own mtime) is kept, so a listing that a key check writes for a `.blend` saved while `gc` runs is not lost. Markers in use keep an old mtime (an unchanged marker is not rewritten), so they are protected by the input set, not by age. `finals.json` is not pruned of `.blend`s no clip uses (small, rewritten by renders: a race for little).
  - **The adapter's memory.** `BlendDeps` remembers each listing in memory and returns its path without checking the file, so a deleted listing was a trap: a `.blend` saved back to an older version would key on a missing file. `gc` calls `BlendDeps.forget` with the folders it removed, and the next key check lists again (one Blender start). Version and range markers are written by `marker()` on every `inputs()` call and need no such care.
  - **`InputsContext.signal`** is aborted by `ClipRenderer.close()` (the daemon stopping). `inputs()` passes it to the listing's `runBlender`, which kills the process tree as for a render's cancel, so a listing (up to 5 minutes) no longer outlives the daemon. The aborted listing is not remembered. The render's own listing calls (which find the listing cached) take no signal: sharing one listing between callers, one caller's cancel must not fail another's.
  - **Also in this slice (slice 4 leftovers):** `findUserInstall` takes a `versioned` rule's out-of-range folder only as a fallback, after the later rules (a `Blender 3.6` folder no longer hides a supported `blender` on PATH; with nothing else it is still returned, so `doctor` says "out of range"); the opt-in real test has a positive control for the driver trap (same library, `--enable-autoexec`, a frame evaluated: the marker must exist), not run yet because no Blender is on the machine that wrote it.
- **Slice 6 (as built, #482): render only the clip's window.** Plugin-local (`plugins/blender` and docs): no protocol, schema, plugin-API (`PLUGIN_API_VERSION` stays `"1"`) or CLI change.
  - **Window.** `renderWindow(clip, fps)` gives `startFrame = floor(in * fps + 1e-3)` and `frames = frameCount - startFrame`, where `frameCount` is still the frame count up to `in + duration` (same 1e-3 of a frame as before, so an end snapped to the frame grid asks for no extra frame, and a start snapped to it skips none). The request to `render.py` is `{ startFrame, frames }` (`startFrame` 0 for an untrimmed clip). `render.py` shows project frame `startFrame + index` through the same `scene_frame(first, index, step)`, so the remap of a scene at another rate and the subframes are unchanged, and names the files `frame_%06d` from 0 for the window alone; the `frame` events carry the window index, `sceneFrame` the real one. The range refusal still checks the last frame of the window (the scene's End frame must reach `in + duration`).
  - **Padding.** The head is not rendered; the encode puts `startFrame` transparent frames before the PNG sequence so file time t is still composition time t: one extra `lavfi` input `color=c=black@0.0:s=WxH:r=<rate>:d=<(startFrame - 0.5) / fps>,format=yuva420p` (half a frame short, so it ends after exactly `startFrame` frames whatever the float error of the rate) joined to the sequence by the `concat` filter, both in `yuva420p`, same libvpx flags and `-fflags +bitexact`. With `startFrame` 0 the command is exactly the plain one, so a clip with no head trim keeps its bytes. Checked with the managed ffmpeg 9.0.1 on a synthetic sequence at 10 fps and 30000/1001: the output has `startFrame` frames of alpha 0, then the sequence, at the exact count.
  - **Progress, written-frames check and estimate** all count the window: `Fra:` lines start at scene frame `first + startFrame`; Blender must write `frames` files; `finals.estimate` (`FinalTimes.estimate`, unchanged) is given the window, so a clip trimmed by 10 s of a 12 s scene asks the 5-minute confirmation on what it draws, not on what it skips. The measured rate (`record`) already came from the frames Blender timed.
  - **Key.** The range marker is `range/<inMs>-<endMs>ms.json` with `{ inMs, endMs }`: a head trim changes the key (it is needed for correctness now, the old render of a larger window no longer covers it). `state-gc.ts` recognises both the new names and the old `<endMs>ms.json` ones, so a project's old markers are swept once no clip names them. Existing renders of trimmed clips are rendered again once; renders of clips with `in` 0 re-render once too, since the marker name changed.
  - **Not verified.** The stub-Blender tests need a POSIX shell, so the Windows machine that built this ran only the pure tests (`renderWindow`, gc names) and the encode command by hand against the managed ffmpeg; it has no real Blender. The opt-in real test has a new case with `in` above 0 (the head is transparent, the first drawn frame is the scene frame the clip's `in` names).

## Side effects

- **Reused:** the plugin API and host as they are (`registerClipType`, the clip job and cache, `.frameshell/` ignored by the watcher as for Remotion), `BinaryManager` and `runDoctor`, the managed ffmpeg and its VP9 flags (ADR 0009), `OFFICIAL_ADAPTERS`, the opt-in real-test pattern. **New, because nothing fits:** the `userInstall` field (a package with no builds already behaved, but its message said "no managed build"), the `inputs` context, the Blender subprocess runner (the Remotion plugin renders in-process; no shared helper exists across plugins, and plugins cannot import each other).
- **Can break:** `ClipRenderer` key checks now call `ensureBinary` for Blender clips on every refresh (a stat, and the global config read); a project with Blender clips and no Blender gets the clip's key error until `binaries.blender` is set. `tools()` now lists `blender` last, which the CLI doctor test pins. `inputs` for other adapters is unchanged (the extra argument is ignored).
- **Security:** the plugin runs only shipped scripts with JSON; `-Y` and `--factory-startup` keep embedded scripts and add-ons out. Under `-Y`, scripted drivers and module text blocks in the `.blend` did not run (Evidence); drivers in linked libraries outside the project are not verified with a real Blender (slice 4 writes the opt-in check). Outside files are allowed (owner, 2026-11-16) and named in a render warning.
- **Shared queue:** unchanged (decision 6).
