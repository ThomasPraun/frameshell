# Review mode and proposals

Moves "opt-in proposal mode per transaction" from v0.2 to v0.14 and amends decision 15. A person who wants to see an agent's edit before it lands turns on **review mode** for the project: each agent transaction then waits as a **proposal** that the person views before and after, and accepts or rejects whole. Off by default; with it off nothing changes. Decided by the owner on 2026-10-22.

## Context (verified in the tree)

- Every change is an operation applied at once: the daemon writes `timelines/<id>.json`, appends `{ op, args, inverse, author, tx, revisionBefore }` to `.frameshell/history/<id>.jsonl` and emits `timeline.changed` (`TimelineService.#record`, `packages/core/src/timeline/service.ts`). Inverses are `timeline.patch` diffs (ADR 0004).
- `TransactionTracker` (`packages/core/src/history/transactions.ts`) groups operations per author: `cli:<session>` automatically until a 10 s idle gap, explicitly with `tx begin`/`commit`/`abort` (persisted in `dataDir`, optional `autoCommitAfter`); other authors get one transaction per operation.
- Authors (SPEC §6.2): a connection whose handshake `client` starts with `desktop/` is `ui`; everything else is `cli:<session>`, `cli`, `agent:<label>:<session>` (`FRAMESHELL_AGENT` or the app's `session.tag`), `file` (watcher) or `plugin:<name>` (`authorOf`, `journalAuthorOf` in `packages/core/src/daemon.ts`). The MCP server is a `cli` client, so Claude Desktop's calls are `cli:<session>` or `agent:…`.
- `planRevert` (`history/revert.ts`) already decides conflicts by entity keys `group:<id>`, `track:<id>`, `clip:<id>` and `order`; `planDiff` (`history/diff.ts`) turns operations into per-clip `added`/`removed`/`moved`/`changed`, which the History panel marks on the timeline (`renderer/src/history/useHistory.ts`).
- Direct edits (SPEC §6.4): `TimelineService.reconcile` journals a valid current-revision edit as `timeline.patch` by `file`, or restores the daemon's version and keeps the edit under `.frameshell/rejected/`. The app's own saves go through `file.write` as `ui`.
- User decisions live in `configDir` (`resolveAppDirs`); project trust is `<configDir>/trust.json` keyed by project root (`plugins/trust.ts`).

**Guiding principle: simple for the person and the agent, optional, nothing mandatory.** One switch, one proposal at a time, accept or reject. An agent that never heard of review mode still works: it is told why it waits and what to call.

## Decision

1. **The switch.** "Review agent changes before applying", per project, off by default, in the app (project menu and the History panel header). While on, every timeline change whose author is not `ui` becomes a proposal: agents, a person typing `frameshell` in a terminal, MCP clients (Claude Desktop), plugins and direct file edits alike. The person's own edits in the app apply at once, as today.
2. **Where the switch lives.** `<configDir>/review.json`, keyed by canonical project root, next to trust. Not in `frameshell.json` or `.frameshell/`: an agent edits project files, and the switch must not change through them. The daemon reads it and is the only writer; internal method `review.set` accepts only author `ui`, so there is no CLI command or MCP tool. Agents read it in `status` and `proposal.status`. A moved or cloned project starts with review off. The guard is against routine agent behaviour, not a hostile process: anything running as the user can write `configDir` or claim a `desktop/` client id.
3. **One proposal = one transaction.** The proposal's id is its transaction id (`tx_…`), its label the transaction's. It is **building** while the transaction is open and **ready** when it closes: `tx commit` or auto-commit for explicit ones, the idle gap for a session's automatic grouping, at once for authors without grouping (`file`, `plugin:<name>`, `cli` without session). So an agent's burst of `cut` calls is one proposal, as it is one History entry today. `tx abort` while building drops it: nothing reached the file. Decisions are whole: accept all or reject all. Partial acceptance is accept, then `revert` single operations from History.
4. **A shadow, not the file.** While a proposal exists, its operations run through the engine against a proposal timeline (current file plus the proposal's patches), never the file. The store keeps, per touched timeline, the base hash and each operation's `op`, `args`, forward patch and inverse, in `.frameshell/proposals/<tx>.json`, written before the operation answers, so a proposal survives a daemon restart (rebuilt by replaying patches on the current file, then checked as in 7).
5. **Reads.** `timeline.show`, `track.list`, `frame` and `inspect.point` take `view`: `current` or `proposal`. Default: `proposal` for the proposal's author (it must see its own effects to keep building), `current` for everyone else. Results say which (`view`, plus `proposal: { tx, state }` or null). `render` always exports the current timeline. `history` and `history.diff` read the journal only.
6. **One at a time; the agent waits.** While a proposal is building or ready, a timeline change by any other non-`ui` author, a new `tx begin`, and any change by its author once it is ready, fail with `ProposalPending` (data: `tx`, `label`, `author`, `state`, hint), message "A proposal is waiting for review (tx_…, "Remove silences"). Run `frameshell proposal wait`, then continue." `proposal.wait { timeout? }` blocks until the proposal is decided and returns `outcome`: `accepted`, `rejected` or `stale` (with `conflicts`), or `pending` after `timeout` (default 300 s, max 3600; MCP clients time out tool calls), so the agent calls again. `proposal.status` returns `review`, the open proposal (state, author, label, operations, timelines, age) and the last decisions. `status` carries the same. `history` lists the decisions after `since` in `proposals`, so `history --since <tx>` tells an agent what became of its last proposal.
7. **The person keeps editing: rebase or stale.** After each `ui` change while a proposal exists, the daemon compares entity keys: if the person's operations since the proposal's base touch none of the keys the proposal's patches touch, the proposal is replayed on the new current timeline and checked against timeline rules (rebase). If keys overlap, or the replay breaks a rule (an overlap, a removed track), the proposal is **stale**: it closes unapplied with `conflicts` (the clip, track or group ids touched by both), the bar says "Out of date: you changed the same clips", and `proposal.wait` returns `stale`. A building proposal that goes stale also ends its transaction; the author's next operation fails with `ProposalState` (reason `stale`) naming the ids. Same keys as `planRevert`, so "touches the same clips" means the same thing for revert and review.
8. **Accept and reject.** `proposal.accept { tx }` and `proposal.reject { tx }` are internal (no CLI command or MCP tool) and refused with `ProposalState` (reason `forbidden`) for any author but `ui`; an agent cannot approve itself. Accept checks 7 again, then journals the proposal's operations in order with their original author, `tx`, label, args and inverses, plus `proposal: "<tx>"` on each entry, all timelines or none (as `revertAll` does). History shows them as the agent's, `revert` works per operation, and `timeline.changed` follows as for any operation. Reject journals nothing; the proposal file stays in `.frameshell/proposals/` for recovery, swept by `gc` after 7 days with stale ones. Every outcome is appended to `.frameshell/proposals/decisions.jsonl` (`tx`, label, author, outcome, conflicts, `at`); `history` and `status` read it.
9. **Direct file edits.** A timeline file edited on disk (author `file`) while review is on is diffed and checked as today; a valid edit becomes a ready proposal labelled `Edit timelines/<id>.json`, the file goes back to the current content (as `#reject` restores it), and the edited text is kept in the proposal file. An edit that is stale or invalid is rejected as today; one arriving while another proposal exists is rejected with reason `proposal-pending`, kept under `.frameshell/rejected/`. The offline catch-up on open (§6.2) follows the same rule. `file.write` by `ui` stays immediate.
10. **Notifications.** `proposal.changed { project, tx, label, author, state, operations, timelines, conflicts? }` on every step (building, each operation, ready, accepted, rejected, stale). `timeline.changed` stays about the file only. The MCP server marks the status resource updated on it.
11. **The app.** A bar above preview and timeline in every window of the project, detached panels included: label, author, operation count, a **Before / After** toggle, **Accept** and **Reject** (Accept only when ready; Reject also while building). The toggle is window state shared with its detached panels (ADR 0012), so preview and timeline always show the same side; it starts on After when a proposal becomes ready. After builds the preview program and the timeline from `view: "proposal"`; the timeline marks what changes with the History diff marks (added, removed, moved, changed), from a `history.diff`-like view of the proposal. Accepting in one window settles it for all; a second click gets `ProposalState` (reason `decided`) and is ignored. Strings in `shared/i18n/`, English and Spanish.
12. **Agents.** MCP tools `proposal_status` and `proposal_wait` come from the registry; accept, reject and `review.set` are internal and never tools. The skill gains a short paragraph: if a change fails with `ProposalPending`, run `frameshell proposal wait`; on `accepted` continue, on `rejected` ask the person what to change, on `stale` re-read the timeline and redo; with review on, group one intent in one `tx begin "<label>"`, because the label is what the person reads.

## Considered options

- **The switch in `frameshell.json`.** Rejected: the agent edits that file; it would also follow the project into git, for people who never chose it.
- **A per-transaction opt-in by the agent** (the v0.2 wording). Rejected: review is the person's choice, not the agent's.
- **Apply at once and keep a reviewable checkpoint** (accept = nothing, reject = revert). Rejected: preview, export and the person would see unreviewed changes, and a reject could conflict with later edits.
- **Queue several proposals.** Rejected: later ones build on earlier ones, and accepting out of order needs a merge model; one at a time keeps the agent's view simple.
- **Per-operation accept.** Rejected: operations of one intent depend on each other (ripple cuts shift later clips); accept then revert covers the rare case.
- **Stale on any edit by the person.** Rejected: one nudge elsewhere would throw away an hour of agent work.

## Consequences

- Protocol bump: `proposal.status`, `proposal.wait`, `proposal.diff` (the History diff marks of the open proposal), internal `proposal.accept`, `proposal.reject`, `review.set`; `view` on the reads in 5; `proposal` on `status`, `history` and `tx.commit` results; `proposal` on journal entries; notification `proposal.changed`; error codes `ProposalPending`, `ProposalState`; rejection reason `proposal-pending`.
- CLI: `frameshell proposal status|wait|diff`. Skill updated (`pnpm gen:skill`).
- `.frameshell/proposals/` joins the project layout; nothing in it is needed to open a project.
- With review on, a person running `frameshell` by hand in a terminal reviews their own commands too: authors say who connected, not who typed.
- Turning review mode off leaves an open proposal open until the person accepts or rejects it; only new proposals stop.
- The app's Ask agent context frames and its `frame` calls read the current timeline even while After is shown.
- Not covered: changes outside timelines (compositions, scripts, transcripts, assets, `frameshell.json`, plugin installs). A changed composition re-renders a clip already on the timeline without review.
